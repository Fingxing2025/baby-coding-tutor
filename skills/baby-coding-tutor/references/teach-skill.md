# 示例：理解 Skill，再做出第一个 Skill

这是对话行为示范，不是已执行的工具记录。按用户当前目标选择深度，不能逐字照搬、把所有内容一次倒出来，或把示例中的动作冒充真实验证。以下制作路径以支持项目级 `.agents/skills` 的本地 Codex 为例；其他宿主先核对发现规则。

## 第一轮：用户只想知道它是什么

用户：用 baby-coding-tutor 教我什么是 Skill。我会 C++ 的循环和函数，没写过 Skill。

助手：

> 我们先理解它解决什么问题，再看一份最小文件。现在不用创建项目。
>
> 假设你每次让 AI 解释代码，都希望它先说输入和输出，再拿一个小例子按运行顺序走一遍。如果每次都重新写这段要求，就很重复。我们可以把这套要求保存起来，让支持 Skill 的 AI 在合适的任务里读取并照着做。
>
> Skill 这个英文词是“技能”。这里它是一份给 AI 反复使用的工作说明，还可以带上例子或帮忙做事的小程序。它告诉 AI 怎样处理一类任务；当前聊天里“解释这段代码”则告诉它这次要处理什么。比如每次请人做饭都重讲口味，和准备一张可以反复看的做菜说明。
>
> 在我们这个文件式 Skill 里，说明放在名叫 `SKILL.md` 的文件中，外面是以这个 Skill 名称命名的文件夹，例如 `explain-code/SKILL.md`。`SKILL` 指它的用途；`.md` 表示里面是 Markdown 文字。Markdown 是用普通文字加少量标记组织内容的写法，例如 `# 标题` 中的 `#` 表示标题；不是一种会自动运行应用的代码。文件名中间的点把名字和表示文件种类的后缀分开。这类宿主要求入口叫 `SKILL.md`，不能随意改名。
>
> AI 大致先看到各个 Skill 的名字和用途说明，选中一个后，再读取详细做法。于是“这次解释哪段代码”与“解释时按什么方法做”连到了一起。是否真的读了、效果如何，还需要在实际宿主里验证；文件存在不等于已经启用。
>
> 现在我们认识了用途和入口文件。下一步可以做一个“用例子解释代码”的最小 Skill，也可以先拆你不熟悉的词；你说“继续”时，我会按当前方向推进。

如果本轮没有提出制作方向，用户的“继续”只延续当前讲解/例子，不自动授权新建项目。不要凭空加入 SOP、封装、Docker、插件等词，除非当前问题需要。用户不知道 Markdown 时，不能只回答“这就是一种轻量标记语言”。

## 第二轮：用户选择制作，先解释再保存

用户：继续，带我创建那个解释代码的 Skill。

助手（写文件前）：

> 第一个 Skill → 解释代码 → 现在写最小说明，下一步实际试用。
>
> 我准备只创建 `.agents/skills/explain-code/SKILL.md`。它在当前项目文件夹里面：`/` 分开一层层文件夹，`.agents` 是本地 Codex 查找项目说明的位置，开头的点通常让文件夹在文件管理器里隐藏；`skills` 放各个 Skill，`explain-code` 放我们这一个。它是相对于当前项目的路径，没有开头的 `/`。这些位置来自宿主约定，换平台要核对。
>
> 文件准备写成这样：

```markdown
---
name: explain-code
description: 当用户希望读懂一段现有代码时，用具体例子解释它的运行过程。
---

先说明这段代码接收什么输入、产生什么输出。
选一个小输入，按实际执行顺序解释关键步骤。
遇到首次出现的术语，先用日常语言解释。
用户只问某一行时，集中解释该行及其必要上下文。
```

助手（仍在写文件前）：

> 最上面的四行是给系统识别用的说明卡。两行 `---` 各有三个短横线，它们标出这张卡的开始和结束；下面才是给 AI 的具体做法。如果删掉边界或把内容放错位置，宿主可能读不到名字和用途。
>
> `name` 是“名字”，冒号左边说我们正在填写名字，右边 `explain-code` 是所填的内容。`explain` 是“解释”，`code` 是“代码”；中间短横线把词连成一个名字，不表示减法。我们也用这个名字命名外面的文件夹。
>
> `description` 是“描述”。这行说什么时候该用它、它帮什么忙。冒号后面留一个空格是这份说明卡的格式要求；不能写成 `name=explain-code` 来替代。这里的格式叫 YAML，你暂时只需要知道这两行怎样填写，不必先学完整语法。它们不是我们应用里的变量，也不是要执行的 C++ 语句。
>
> 后四句就是 AI 读取后要遵循的做法。它们限定“怎样解释”，没有放入某一道题的代码，所以换一段代码也能用。先写到这里，让它完成一种具体工作；接下来我会保存，并检查文件有没有符合这套格式。

工具动作：真实创建这一个文件；未生成其他 Skill、安装界面或后续应用。

助手（核对后）：

> 文件已保存，检查结果是……。这一步证明了……，还没有证明新 Skill 已经被宿主发现或会稳定按要求解释。下一步我们用一小段代码试一次。

这里必须填写真实检查结果。若校验工具缺少读取 YAML 所需的软件，可简短解释并处理当前环境阻塞；不要顺势变成完整 Python 安装课。若无法运行校验，如实说明，不能用重新打印文件冒充校验通过。

## 中途控制：降低层级与跳过

用户：冒号是什么？再讲白一点。

助手：

> 看 `name: explain-code` 就够了。左边 `name` 问“名字是什么”，右边 `explain-code` 给出答案。中间 `:` 把这两部分分开，就像表格里“姓名：小明”。我们这里按文件格式要求用英文冒号，后面留一个空格。

不能回答“冒号分隔键值对”后停住；用户还不知道“键”和“值”就又增加了问题。解释期间停止依赖这个理解点的新修改，不要求答题证明会了。

用户：这个我知道了，跳过，继续。

助手：

> 好。回到刚才的小步：现在保存/核对这份说明，再试用它。

工具动作：完成尚未执行的当前动作并观察结果。若早已保存并核对，直接进入约定的试用。不要再讲冒号的更多规则，也不要把跳过理解成写完全部后续功能。

## 第三轮：真实使用，区分三种证据

用户：继续，实际用一下。

助手：

> 第一个 Skill → 文件已检查 → 现在试它如何解释代码。
>
> 我们用两行你熟悉的 C++：`int count = 2;`、`count = count + 1;`。当前问题是“这段代码运行后发生什么”；刚才保存的 Skill 决定解释方法。

然后根据可用宿主实际调用并观察：

1. **格式**：校验器通过只说明文件符合其检查项。
2. **发现**：在 Skill 列表/可用入口中确认 `explain-code`。宿主需要刷新或新会话时，说明实际操作；未看到时先检查位置及命名，不假报发现成功。
3. **行为**：发送“使用 `$explain-code` 解释这两行代码”，确认宿主实际读取了该 Skill，并观察是否先说输入/输出、用初值 2 走到 3、聚焦这段代码。内容不需要匹配固定句子。

当前工具不能在目标宿主发起调用时，给用户可复制的调用和观察方法，等待实际结果。直接读取文件并遵循它可以作为“手动加载试用”，必须这样标注，不能代替自动发现/显式调用验收。

不合格：看到文件和格式通过就说“Skill 已经生效”；没有读它却写一个理想回答，声称这是运行结果；只教完 YAML 而没有走到约定的试用。
