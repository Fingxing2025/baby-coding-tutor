# Test 4：教我什么是 Skill，再一起创建

这是多轮行为回归方案，不要求回答某套固定词句，也不替代前三个真实项目的完成验收。[一次模型试跑记录](../../docs/TEACHING-SIMULATION-v0.1.1.md)覆盖了创建前解释、降层和跳过后的手动试用；正式宿主发现/调用与真人体验尚未验收，不能算本方案全部通过。

## 要检验什么

代码只写几行，也可能把关键解释留到施工之后。本测试检查：工程范围保持小步，解释能主动覆盖当前必要含义；必要下层拆解不被当作新课程或“一词一轮”。

假定用户会 C++ 的变量、循环、函数，不会 Skill、Markdown、顶部信息块、安装发现和工程命令。明确会的内容不重复，不考试。

## 准备与证据

1. 观察者创建独立空项目，按仓库 [安装说明](../../README.md) 安装完整的 `baby-coding-tutor`，确认当前宿主能发现它。不要把完整测试脚本发给教学 AI。
2. 保留初始文件快照及每轮对话、工具动作、文件差异。安装 tutor 的现成文件是测试准备，不是教学 AI 提前实现了学习成果。
3. 使用具备文件编辑和运行工具的宿主。可用的校验工具先由观察者检查；缺工具/依赖时记录“环境受阻”，不据此判教学失败，也不隐瞒受阻。

调用不通时可另试显式指定 tutor 的实际 `SKILL.md` 路径，但单独记为回退，不能算自动发现通过。

## 多轮输入与观察

### 1. 先理解，不自动开发

发送：

```text
用 baby-coding-tutor 教我什么是 Skill。
我会 C++ 的变量、循环和函数，没有项目经验，也不懂 Markdown 和 Skill 文件结构。
```

观察：从“为什么要重复使用一套要求”讲到 Skill 的直觉含义、当前场景和具体例子；能区分说明内容与承载它的文件。可以只读现有 tutor 作例子，不擅自新建项目、生成文件或安排整套课程。

失败：只给定义和“继续再说”而缺少必要关系；用未解释的 Prompt、SOP、元数据等词作定义；为了工程进展直接新建另一份 Skill。

### 2. 用户选择创建

发送：

```text
可以，带我创建一个叫 explain-command 的最小 Skill：遇到陌生命令时拆开解释。
文件放在当前项目里。我不懂 .md、文件头和它们的写法；请一小步一小步做。
```

观察第一次写文件之前的说明，而非只看最终总结。需要把拟写内容与当前意义连起来：

- `SKILL.md` 是当前宿主读取的核心说明文件；`.md` 表示以 Markdown 这种文字排版约定保存，不意味着里面必须是程序代码。
- 两条 `---` 划出顶部信息块，让名字和用途与正文做法分开。
- `name` 是名字、`description` 是描述用途与适用时机；关键字按宿主约定写，右侧才是自己的内容。
- `name: explain-command` 中，冒号把这项信息的名字与对应内容分开；不能只说“键值对”而不解释。
- 顶部信息帮助宿主识别/选择；正文写实际做法。说明这些角色后再落盘，不把格式合格等同于已经被宿主发现。

允许用一种核心结构解释覆盖这些必要含义，不必每个词单独停一轮，也不要求先上 Markdown/YAML 课程。文件和代码保持 tutor 的小步额度；做法内容由当前目标决定，不扩展为复杂命令教学系统。

失败：只说“上半部分是名片”就写入，完成后才首次解释字段和符号；因为有多个陌生词便截断必要说明；讲完整套格式语言却一直不创建。

### 3. 真正降层

发送：

```text
再讲白一点。我没明白 name: explain-command：冒号前后分别是什么？
为什么 name 不能直接写成“名字”？先停在这个点。
```

观察：回到这行文字，具体说明左边告诉读取者“这是什么信息”，右边填写自己的名字；宿主按约定识别 `name`，换成中文可能无法识别。若使用“读取者”，应说明这里指会读取文件的宿主程序。暂停依赖这个理解点的新增施工。

失败：只换成“这是 YAML 键值映射”或“标准语法”；缩短原句但不说明实际动作；无视疑问继续写文件。用户不用回答题目证明理解。

### 4. 跳过后实际推进

发送：

```text
这部分跳过，继续。让我们试用刚写的 Skill，解释 python3 --version；不用执行这个命令。
```

观察：立即结束冒号的解释，不补尾课、不考试。按当前进度完成必要的最小文件/校验，或读取已完成的 Skill 并实际按要求解释命令；不扩大成后续所有功能。遵守“不执行命令”，格式校验等其他必要操作说明用途和范围即可。

失败：仍讲“不过冒号你必须知道”；要求答题；只说以后能试而无操作证据；执行用户明确要求不运行的命令。

## 分开确认格式、发现、使用

观察者分别记录：

| 层次 | 需要的证据 | 不能据此声称 |
| --- | --- | --- |
| 格式 | 校验工具实际输出；没有工具则说明手动检查及限制 | 已安装、自动发现或教学规则生效 |
| 宿主发现 | 学习成果放在宿主支持的位置，并在该项目的技能列表/选择器或新对话中被识别 | 只因文件存在就称发现成功 |
| 实际使用 | 助手读取该 Skill，并按它拆解当前命令；保留动作与回答 | 输出看起来不错就推断确已加载 |

宿主支持时，观察者另开同项目新对话，发送“使用 $explain-command，解释 python3 --version，不运行命令”。若不能发现，记录失败/受阻原因；直接读取文件再试作为单独回退，不能覆盖发现结果。无需反复要求用户批准常规小操作。

校验依赖缺失属于支持性环境故障，可简述实际问题、修复范围和未验证边界；不要求把它扩展成业务 Debug 课程，也不能报假成功。

## 判定

按 [验收标准](../ACCEPTANCE.md) 记录适用项，重点看 A02–A06、A10、A13–A16。观察核心顺序与含义，不统计回答字数、不做生成文字断言。跳过、降层和调用需要实际触发；未观察不能算通过。

项目完成要求此处限于约定的最小 Skill 成果及其可用性证据，不表示 Todo、前后端项目或完整 Debug 教学已通过。用户自己的体验单独记录，不由模型断言“学生已经理解”。
